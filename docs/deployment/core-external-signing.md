# Core external-signing workflow candidate (unreleased)

This increment creates exactly eight linked libraries and one new Manager, with the explicit initial governor `0xd76AD27a1Bcf8652e7e46BE603FA742FD1c10A99`. It contains no governor CALL, optional helper/router creation, metadata attachment, ENS custody/approval/fuse change, activation, or transaction targeting an existing deployment. An independent new deployment does not require settling, migrating, pausing or modifying old Manager/CFA/B3AA contracts. Existing jobs, reserves, permissions and funds remain untouched.

## Status and trust boundary

This is offline functional implementation. Production use requires a separately reviewed clean source revision, a pinned build catalog, complete operational qualification and user-controlled signing. The local synthetic catalogs/tests are **not usable production qualification**. No release identity is selected. The initial contract candidate's functional review is not a security audit. The owner accepted omission of an external independent audit and Sepolia rehearsal. These are recorded omissions, not passes. This does not clear unresolved correctness, authority, provider, hardware or release gates.

Creation wallet semantics and signing transport are separate:

* `empty-eoa-direct-create.v1` requires empty account code at the reviewed canonical pin and immediately before each handoff/relay.
* `delegated-eoa-direct-create.v1` supports outgoing direct type-2 CREATE from an already-delegated EOA. It requires an exact 23-byte EIP-7702 marker, exact target runtime, complete reviewed state getter checks and source/build/block/Osaka-bound evidence reports. The coordinator never installs, removes or changes delegation.
* Contract wallets, factories, batched/wrapped calls, self-calls, type-4 creation envelopes, automatic broadcast wallets and wallets that cannot return the exact serialized signed type-2 transaction are unsupported.
* A policy evidence hash binds an operator-selected report. A `pass` field does not establish independent review or real wallet custody. The historical 6c8 target and actual hardware route have not been qualified.

The transport is SDK-independent. A hardware application may return a signature which a separate user-controlled adapter assembles into the exact type-2 raw transaction. The coordinator recovers the sender and compares every field. No Ledger SDK/device/key handling is included. Ledger DMK/Ethereum SignerKit is a researched candidate route; package/context/origin-token behavior and physical-device qualification are outstanding. There is no tokenless/offline-hardware promise.

## Required operator inputs

1. An independently reviewed **clean Git checkout**, expected commit/tree, both lockfile hashes and pinned catalog SHA-256/build ID. The CLI observes its own actual checkout; it cannot trust a revision supplied only by the plan. Catalogs bind exact standard-JSON compiler input/output, all compiler source files, all nine artifacts and constructor schemas. No newest-artifact selection or fallback build is allowed.
2. An explicit creator address, starting nonce, sender policy and (for delegated mode) three independently reviewed evidence reports. Their exact scope includes creator/target/runtime, complete state checks, source/lock hashes, catalog/build digest, canonical block number/hash and Osaka execution fork.
3. Explicit acknowledgement of the requested d76 governor; canonical mainnet USDC; base URI; ENS registry/wrapper; four membership roots; two Merkle roots; and the two settlement fee wallets. Existing membership dependencies are read-only inputs. No treasury or ENS custody change is inferred from these fields.
4. A reviewed canonical pin and expiry (at most 2,048 blocks later), nine exact gas/fee envelopes and a maximum aggregate fee budget. Each transaction is type 2, chain 1, `to: null`, value zero and empty access list. Gas must be at most 16,777,216 and fit the observed block limit. No fee bump is automatic. Funding is the user's responsibility.
5. A pre-existing operator-selected shared creator nonce-lock directory, coordinated with all other deployment tools and all external signing activity. The shared `creator-nonce-lock-v1` namespace is chain plus actual sender. Local locks cannot prevent another host, wallet or program from signing with that sender.
6. Separately selected read RPC and raw-relay RPC endpoints. Read methods are HTTPS-only, bounded, sequential and allowlisted. Production requires EIP-1898 canonical object tags; there is no numbered-block fallback. Reports never contain endpoint credentials.

## Command sequence

Use the pinned Node 22 runtime and `hardhat/scripts/core-session.cjs`. Every command requires `--catalog`, `--catalog-sha`, `--build-id` and a fresh `--out` path. The output path must not exist and must be outside the reviewed source checkout. The CLI reserves it before any one-time action. A reserved/incomplete output is not a successful report; `retrieve-handoff --session ...` can recover the original persisted handoff without new signing authorization. In exactly the durable signed state, it revalidates the saved raw bytes and returns the original relay acknowledgement; any recorded or independently marked attempt suppresses that acknowledgement. Output, verification-export, session and lock paths are resolved and rejected inside the reviewed checkout before qualification or file creation, including symlink aliases. Read-dependent commands use `MANAGER_READ_RPC_URL`; only the explicit `relay` command uses `MANAGER_RELAY_RPC_URL` and imports the raw relay.

1. `plan --config config.json`: entirely offline; derives nine contiguous CREATE addresses and exact linked initcode/constructor arguments. Its status remains `readyToBroadcast: false`.
2. `preflight --plan plan.json`: read-only checks source, canonical pin, actor/governor code, delegated state, nonce, dependencies, USDC conditions, predictions, gas and fees. Nothing is reserved or signed.
3. `start --plan plan.json --session /absolute/new-session --lock-directory /absolute/shared-locks`: reserves the creator and durably stores the plan/session. An unsuccessful start retains the lock for reconciliation.
4. `handoff --session ...`: rechecks the exact finalized prefix and current state; durably records the single signing handoff **before** returning its unsigned bytes and envelope. Do not sign twice, auto-broadcast, alter fees/nonce, or reuse a handed-off nonce.
5. The user signs that exact transaction externally. Put only `{ "raw": "0x02..." }` in a private local file.
6. `import --session ... --signed-file ...`: offline signature recovery and exact envelope comparison; stores the capability privately and durably records its known transaction hash. It returns an exact relay acknowledgement token.
7. `relay --session ... --acknowledgement ...`: a separate **user-run** action. Rechecks source/state/nonce and exact signed bytes, saves an immutable submission marker and attempted event before the one raw submission. It never retries, fee-bumps or signs. This implementation task did not execute this command against any live endpoint.
8. `recover --session ...`: read-only canonical transaction/receipt recovery. It can recover an externally broadcast hashless handoff using a bounded 2,048-block scan. Missing, pending, replaced, ambiguous, failed or mismatching transactions never authorize a resend. `reconcile --session ...` repeats proof checks and records the finalized exact prefix locally.
9. Repeat steps 4–8 for the next operation only. `complete --session ...` requires all nine finalized receipts, full linked runtimes, current creator/governor policy and paused/unconfigured direct Manager state. It releases only the matching local creator lock. Result: `CORE_CREATED_PAUSED_CONFIGURATION_SEPARATE`, activation unauthorized, explorer acceptance unobserved, comprehensive authority finalization still requiring separate review.

A lost relay response is an ambiguous outcome: the saved hash and attempted marker survive and make another relay impossible. Recover instead. An existing identical raw file after an interrupted import can complete its missing signed event without re-signing or replacing bytes. Terminal completion can safely release its retained matching lock after interruption, using a token-bound atomic rename before cleanup. An empty original lock pathname is never assumed to belong to the old session: it could be a concurrently starting new session. Only the uniquely named release tombstone can be cleaned after its owner record has been removed.

## Crash handling and local integrity

The session has exclusively created hash-chained event files and a separately fsynced head, plus immutable per-operation attempt markers. Missing/truncated/reordered records, a missing final tail, altered signed bytes, wrong creator/chain lock, occupied prediction or nonce drift fail closed. A complete single event written before a head-update interruption is inspectable with `inspect-journal --session ...`; `repair-journal --session ... --acknowledgement ...` can acknowledge that exact existing conservative event. It cannot synthesize a missing tail or roll state backward. No chain transaction is sent by journal repair.

An `active-command` process lock is never automatically stolen, including after a process crash. Preserve it and establish that the original process is stopped before a separately reviewed manual local recovery. No automatic stale-process lock-removal command is supplied in this increment. Read-only receipt recovery remains possible if the committed journal/head are intact. Startup interruptions before a complete session identity, missing-tail corruption and incomplete attempt/event writes may likewise require explicit manual reconciliation. These stops prioritize no duplicate signing/submission over automatic liveness.

Filesystem integrity and operator control are required. The head/attempt markers detect interrupted writes and accidental tail deletion, not malicious rollback of every file by a host administrator. No local journal can revoke signed bytes already handed to an external signer or broadcaster.

## Verification export and historical compatibility

`export-verification-package.cjs` produces an offline predicted-address verification package: original compiler input/settings, exact per-contract FQN, seven Manager constructor arguments, library links, ABI and hashes. It refuses supplied receipt claims; it does not submit to or claim acceptance from an explorer. Receipt evidence comes from the session verifier and remains a separate package.

The catalog requires explicit selection between historical six-argument Manager and new seven-argument Manager constructors. An old artifact is never decoded as the new ABI. Existing v114 gates, archived exact artifacts, old receipts, selected Builder ab516 history, old deployment profiles and historical runtime identities remain unchanged. The new getter is additive; a historical private-field build still has no getter and must remain marked unobserved where appropriate.

## Test interpretation

Tests use disposable keys and a local Osaka EVM with the ordinary 30-million block gas limit and no coverage gas-cap override. They install a synthetic local delegation using a genuine type-4 transaction, then exercise outgoing type-2 creation. EDR lacks EIP-1898 tags and real finalized consensus: a clearly test-only adapter brackets genuine numbered EVM calls with canonical hash checks and maps finalized to local latest. Production has neither fallback. These tests do not qualify a public provider, consensus/finality, real delegate, Ledger, explorer, or external independent audit, which remains an expressly accepted omission rather than a completed check.
