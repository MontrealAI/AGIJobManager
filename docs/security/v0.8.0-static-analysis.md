# v0.8.0 extended static-analysis review

Reviewed on 2026-09-17 with Slither 0.10.4, Foundry 1.7.1 and Solidity 0.8.23. This is an internal engineering review, not an independent audit or proof that the system is free of vulnerabilities.

The older Slither configuration excludes entire detector families. v0.8.0 adds a separate mandatory review gate that runs those families and retains their findings. It scans production contracts; dependencies, test contracts and historical contracts are excluded from reported findings. The dependency lockfile and every production Solidity file are bound to the review by SHA-256.

## Results and scope

| Scan | Detectors | Analyzed contracts | Findings |
| --- | ---: | ---: | --- |
| All medium/high detectors, no detector-family exclusions | 53 | 109 | 5 high, 15 medium |
| All five reentrancy detectors, including low/informational severities | 5 | 109 | 1 medium, 30 low |

The medium reentrancy finding occurs in both reports: there are **50 distinct findings**, represented by 51 report entries. There were no `reentrancy-eth` or `reentrancy-unlimited-gas` findings. Each retained finding has an exact identifier, severity, confidence, location, rationale and code/test evidence in [`slither-reviewed-findings.json`](../../scripts/security/slither-reviewed-findings.json).

No exploitable defect was confirmed from these findings under the deployment assumptions below. The result is **reviewed findings**, not a claim of zero analyzer findings.

## Medium/high triage

| Detector | Count | Review conclusion |
| --- | ---: | --- |
| `encode-packed-collision` | 5 | Literal URI/ENS-label concatenation, not an authorization hash or signature preimage. ENS prefixes cannot end in a digit, and the exact label is snapshotted and checked against reuse by another job. |
| `divide-before-multiply` | 1 | Slashing intentionally floors each validator's individual deduction first. The sum distributed must equal those actual deductions. Rounding residuals are returned to the winning party. |
| `mapping-deletion` | 1 | Only unassigned jobs can be cancelled or delisted; they cannot have votes. Their mapping entries are empty, and monotonically increasing job IDs are never reused. Both entry points hold the reentrancy guard. |
| `reentrancy-no-eth` | 1 | The write after a transfer updates reputation. Settlement entry points are guarded, terminal state/reserve effects precede outbound payments, and canonical USDC does not invoke recipient hooks. A reputation getter does not grant authority over escrow. |
| `uninitialized-local` | 5 | Boolean flags and integer rewards intentionally use Solidity's false/zero defaults. They are scalar locals, not storage pointers. |
| `unused-return` | 7 | Five calls intentionally select only relevant fields from a decoded job tuple. Two ENS calls independently compute the namehash instead of trusting a returned value; wrapped legacy adoption also verifies ownership. |

## Additional reentrancy triage

Six low `reentrancy-benign` findings concern manager balance counters, cancellation state, or completion metadata after external calls. All affected money-moving entry points hold `nonReentrant`; incoming funds must pass an exact balance-delta check before reserve accounting. NFT receiver callbacks cannot reenter settlement, withdrawal or wallet rotation. Existing and v0.8.0 adversarial tests exercise callback, failed-transfer and rollback behavior.

Twenty-four low `reentrancy-events` findings concern ENS metadata events emitted after configured registry/resolver calls or `onlySelf` dispatch. External entry points enforce `onlyOwner`, `onlyJobManager` or `onlySelf`. ENS integration code is explicitly owner-selected and best-effort; a compromised configured integration could affect metadata or event ordering. These events are not payment authority. Integrators must treat the manager's job state and transaction/log order as authoritative for settlement.

## Mandatory regression gate

Run from the repository root after installing the locked dependencies and the pinned toolchain:

```sh
npm run slither:extended
```

The runner performs a fresh Foundry build, writes `build/security/slither-extended.json` and `build/security/slither-reentrancy.json`, and checks both against the reviewed baseline. Findings remain visible in the raw reports and CI artifacts. The gate fails on an analyzer error, an unreviewed/new finding, a removed expected finding, a severity/confidence change, a changed production file set, or a source/configuration/dependency hash change. Removed findings also require review so a broken or narrowed scan cannot silently pass.

Do not automatically regenerate the baseline to make CI green. Inspect each changed finding and its call paths, run relevant adversarial/regression tests, record the rationale, and only then update the reviewed hashes and identifiers. Twelve local negative qualification checks rejected analyzer failures/errors, missing detector output, new/removed/duplicate findings, severity drift, source hash/file-set drift, an incorrect analyzer version, an empty report requirement and missing review rationale.

## Deployment assumptions and limits

- The token is native Circle USDC at the documented Ethereum address. A six-decimal callback token is not an approved substitute. Circle's pause, blacklist and upgrade powers remain external dependencies.
- The owner and moderators have documented operational authority. These scans do not prove that a malicious or compromised privileged operator cannot exercise that authority.
- ENS configuration and completion metadata are optional integrations, not payment truth or trustworthy user content.
- Static analysis is one component of qualification. Unit, fuzz, stateful invariant, browser and deployment checks provide separate evidence; their results must be read alongside this report. These scans neither deploy a contract nor validate a particular live owner/wallet configuration.
